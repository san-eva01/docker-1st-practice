1. Introducción y objetivos

En esta práctica se diseñó, construyó y verificó una aplicación web distribuida en cinco contenedores orquestados con Docker Compose. La aplicación es un sistema de reservación de espacios. Permite registrar, consultar, modificar y eliminar reservaciones de auditorios, laboratorios y salas.

Los cinco servicios se comunican por una red interna llamada app_network y se encuentran entre sí por su nombre de servicio. MariaDB conserva los datos en un volumen nombrado. Redis guarda en caché el listado y cuenta las consultas. Mailpit captura un correo de prueba cada vez que se crea una reservación.

Objetivos cumplidos:

  • Se construyeron imágenes propias para el frontend y el backend mediante Dockerfile.
  • Se definieron y ejecutaron los cinco servicios desde un único archivo compose.yaml.
  • Se configuró una red interna y se usaron los nombres de servicio como host.
  • La información de MariaDB se conserva en un volumen nombrado.
  • Redis funciona como caché con TTL y como contador de consultas.
  • El backend genera una notificación de correo que se puede ver en Mailpit.
  • Se aplicaron health checks, depends_on, variables de entorno y política de reinicio.
  • La solución se verificó con comandos, registros y pruebas funcionales.

5. Desarrollo de la práctica por etapas

Etapa 1. Preparación

Se creó la estructura de directorios y el archivo .gitignore, que excluye .env. También se creó .env.example con valores de ejemplo. El archivo .env local tiene contraseñas generadas aleatoriamente. Se eligió el dominio asignado y se diseñó init.sql con una tabla, una llave primaria, restricciones y tres registros iniciales (sección 2).

Archivo compose.yaml

Este es el archivo completo que define los cinco servicios, la red app_network, los volúmenes, los health checks, las dependencias y la política restart: unless-stopped:

# Práctica individual: Docker Compose con cinco servicios
# Sistema asignado: Reservación de espacios (último dígito 8)
name: reservaciones

services:

    build: ./frontend
    restart: unless-stopped
    ports:
      - "${FRONTEND_PORT:-8081}:80"   # único acceso público a la aplicación (8081 por defecto)
    depends_on:

      - app_network

  backend:

      DB_PASSWORD: ${DB_PASSWORD}

      REDIS_PASSWORD: ${REDIS_PASSWORD}
      CACHE_TTL: ${CACHE_TTL:-60}

Etapa 2. Base de datos y Redis

  • db: usa la imagen mariadb:11.4 con --port=5432. El volumen nombrado MariaDB_data se monta en el directorio de datos y init.sql se monta en /docker-entrypoint-initdb.d/. El health check ejecuta un SELECT 1 por TCP con el usuario de la aplicación, así que solo pasa cuando la inicialización terminó.
  • redis: usa la imagen redis:7.4-alpine con persistencia AOF (--appendonly yes), contraseña (--requirepass) y el volumen redis_data. El health check es redis-cli ping.

Etapa 3. Backend

El Dockerfile del backend parte de php:8.3-apache e instala las extensiones pdo_mysql (para MariaDB) y redis (phpredis, mediante PECL). La directiva FallbackResource envía todas las rutas a index.php, que funciona como router de la API.

FROM php:8.3-apache

# Extensiones: pdo_mysql para MariaDB y phpredis para Redis
RUN docker-php-ext-install pdo_mysql \
    && pecl install redis-6.1.0 \
    && docker-php-ext-enable redis \
    && rm -rf /tmp/pear

# Todas las rutas que no sean archivos se atienden con index.php (router de la API)
RUN echo 'FallbackResource /index.php' > /etc/apache2/conf-enabled/api-router.conf \
    && echo 'ServerName backend' > /etc/apache2/conf-enabled/servername.conf \
    && printf '<Directory /var/www/html/lib>\n  Require all denied\n</Directory>\n' > /etc/apache2/conf-enabled/deny-lib.conf

COPY src/ /var/www/html/

EXPOSE 80

La conexión usa las variables de entorno DB_HOST=db, DB_PORT=5432, REDIS_HOST=redis, REDIS_PORT=6379, SMTP_HOST=mailpit y SMTP_PORT=1025. Ninguna dirección es localhost. Este es el fragmento que implementa la caché y el contador en el listado:

$redis = redis_client();
$consultas = $redis->incr(CONTADOR);              // contador_consultas
$clave = cache_key($buscar);                       // reservaciones:lista
$cache = $redis->get($clave);
if ($cache !== false) {                            // HIT: respuesta desde Redis
    header('X-Cache: HIT');
    $registros = json_decode($cache, true);
} else {                                           // MISS: consulta a MariaDB
    header('X-Cache: MISS');
    $registros = db()->query('SELECT * FROM reservaciones ORDER BY fecha, hora_inicio')->fetchAll();
    $redis->setex($clave, cache_ttl(), json_encode($registros));   // TTL 60 s
}

Cada POST, PUT o DELETE llama a cache_invalidar(), que borra la clave del listado y las claves de búsquedas. Así la caché nunca entrega datos viejos después de un cambio.

Etapa 4. Mailpit

El backend incluye un cliente SMTP mínimo (lib/Mailer.php). Se conecta a mailpit:1025 con fsockopen y envía los comandos EHLO, MAIL FROM, RCPT TO y DATA. Cuando se crea una reservación, envía un correo HTML con sus datos al correo del solicitante. Mailpit es solo una herramienta de desarrollo: captura el mensaje y lo muestra en su interfaz web, pero no entrega correo real.

Etapa 5. Frontend y proxy

El frontend es una página HTML, CSS y JavaScript servida por Nginx. El JavaScript usa la URL relativa /api y nunca localhost. Nginx reenvía /api/ a http://backend:80 y quita el prefijo. Se usa el DNS interno de Docker (127.0.0.11) con una variable para que Nginx vuelva a resolver el nombre backend si el contenedor se reinicia y cambia de IP.

server {
    listen 80;
    server_name _;

    # DNS interno de Docker: resuelve "backend" en cada petición,
    # así Nginx sigue funcionando si el contenedor del backend se reinicia y cambia de IP.
    resolver 127.0.0.11 valid=10s ipv6=off;

    root  /usr/share/nginx/html;
    index index.html;

    # Archivos estáticos
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Proxy de /api/ hacia el backend: /api/reservaciones -> http://backend/reservaciones
    location /api/ {
        set $backend_upstream http://backend:80;
        rewrite ^/api/(.*)$ /$1 break;
        proxy_pass $backend_upstream;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout    15s;
    }
}

Solo frontend y mailpit publican puertos. En la columna PORTS, db, redis y backend no tienen el prefijo 0.0.0.0:. El valor 3306/tcp que aparece en db es solo el puerto declarado en la imagen de MariaDB, y no está publicado.

11.3 Recuperación

Con el backend detenido, Nginx responde 502 Bad Gateway. Al volver a iniciarlo, la aplicación recupera su operación sin reiniciar Nginx, porque Nginx vuelve a resolver el nombre backend con el DNS interno.

12. Resolución de nombres por DNS interno

Docker Compose crea la red de usuario reservaciones_app_network y conecta a ella los cinco contenedores. Cada red de usuario tiene un servidor DNS interno en 127.0.0.11, que aparece como nameserver en el /etc/resolv.conf de cada contenedor. Ese servidor registra el nombre de cada servicio como alias de la IP de su contenedor:

  • db: el backend se conecta a db:5432 y el DNS devuelve la IP del contenedor de MariaDB (172.20.0.2).
  • redis: el backend se conecta a redis:6379 y obtiene 172.20.0.3.
  • mailpit: el backend envía SMTP a mailpit:1025 y obtiene 172.20.0.4.
  • backend: Nginx reenvía /api/ a http://backend:80 y obtiene 172.20.0.5.

Las IP pueden cambiar cuando un contenedor se recrea, pero el nombre se mantiene. Por eso la configuración usa nombres de servicio y nunca IP fijas ni localhost. Dentro de un contenedor, localhost es el mismo contenedor.

13. Seguridad

  • Las contraseñas están solo en .env, que está excluido en .gitignore. En el repositorio se incluye .env.example sin valores reales.
  • Redis requiere contraseña (--requirepass). El backend usa un usuario de aplicación de MariaDB, no el usuario root.
  • No se usa privileged, no se monta /var/run/docker.sock y no se usa container_name, lo que permite escalar servicios.
  • Solo se publican los puertos 8081 y 8025. MariaDB, Redis y el backend son accesibles únicamente por la red interna.
  • La carpeta lib/ del backend no se puede abrir por HTTP (responde 403). Las consultas usan sentencias preparadas (PDO), lo que evita inyección SQL. El frontend escapa el HTML de los datos.

14. Mejora individual: filtro de búsqueda

Se agregó un campo de búsqueda en la interfaz. Envía GET /api/reservaciones?buscar=texto, y el backend busca el texto en el espacio, el solicitante y el correo con LIKE y parámetros preparados. Cada búsqueda se guarda en caché con su propia clave (reservaciones:buscar:<md5>), y esas claves también se borran cuando hay cambios. Involucra al frontend, al backend, a MariaDB y a Redis.

16. Notas técnicas

Imagen, puerto y ruta de MariaDB. La guía pide la imagen MariaDB:16-alpine, el puerto 5432 y la ruta /var/lib/MariaDB/data. Esos valores corresponden a PostgreSQL: MariaDB no tiene versión 16, su puerto por defecto es 3306 y su directorio de datos es /var/lib/mysql. Para cumplir con lo pedido de forma funcional:

  • Se usó mariadb:11.4, la versión LTS vigente, con versión explícita.
  • MariaDB se inició con --port=5432 para respetar DB_PORT=5432.
  • El volumen nombrado MariaDB_data se montó en /var/lib/mysql, que es el directorio real de datos.

El puerto del frontend se puede cambiar con la variable FRONTEND_PORT (por defecto 8081), por si otro proyecto ya ocupa ese puerto. Las capturas de terminal se tomaron de una consola real de Windows PowerShell, ejecutando cada comando dentro del directorio del proyecto.

17. Preguntas de reflexión

1. ¿Por qué el backend debe usar db:5432 y no localhost para conectarse a MariaDB?
Cada contenedor tiene su propio espacio de red. Dentro del contenedor del backend, localhost es el propio backend, donde no hay ninguna base de datos. db es el nombre del servicio, y el DNS interno de Docker lo convierte en la IP del contenedor de MariaDB dentro de app_network.

2. ¿Cuál es la diferencia entre ports y expose en Docker Compose?
ports publica un puerto del contenedor en la máquina anfitriona (por ejemplo, 8081:80), así que se puede acceder desde fuera de Docker. expose solo documenta el puerto y lo deja disponible para otros contenedores de la misma red, sin publicarlo en el host.

3. ¿Qué información permanece cuando se elimina un contenedor y por qué?
Permanece lo que está en volúmenes (MariaDB_data, redis_data) o en bind mounts, porque se guarda fuera de la capa de escritura del contenedor. Lo que se escribió dentro del sistema de archivos del contenedor se pierde. Las imágenes tampoco cambian.

4. ¿Qué problema resuelve el health check antes de iniciar el backend?
Que un contenedor esté iniciado no significa que el servicio esté listo. MariaDB tarda unos segundos en inicializarse y ejecutar init.sql. Con depends_on: condition: service_healthy, el backend arranca cuando db y redis ya aceptan conexiones, y así se evitan fallos de conexión al iniciar.

5. ¿Cuándo puede una caché devolver información desactualizada y cómo lo evitaste?
Ocurre cuando los datos cambian en MariaDB mientras la copia en Redis sigue vigente. Para evitarlo, el backend invalida la caché en cada POST, PUT y DELETE: borra reservaciones:lista y las claves de búsqueda. Además, las claves tienen un TTL de 60 segundos como límite.

6. ¿Por qué Mailpit no debe considerarse un servidor de correo de producción?
Mailpit no entrega los mensajes a sus destinatarios: solo los captura para revisarlos. Tampoco ofrece, por defecto, autenticación, TLS, colas con reintentos, SPF/DKIM ni almacenamiento duradero. Está diseñado para pruebas en desarrollo.

7. ¿Qué servicio escalarías primero y qué cambio harías para evitar conflictos de puertos?
El backend, porque no guarda estado: el estado está en MariaDB y Redis. Para escalarlo, no debe publicar puertos en el host (en este proyecto usa expose) ni tener container_name. Así se puede ejecutar docker compose up -d --scale backend=3: Nginx sigue llamando a backend y el DNS de Docker reparte las peticiones entre las réplicas. Si se escalara un servicio con puerto publicado, habría que quitar el puerto fijo o usar un rango.

8. ¿Qué riesgos existirían si MariaDB y Redis se publicaran hacia Internet?
Ataques de fuerza bruta contra las contraseñas, robo, modificación o borrado de datos, explotación de vulnerabilidades conocidas, ransomware que borra bases expuestas, y abuso de Redis para escribir archivos o ejecutar comandos (CONFIG SET) o para consumir recursos (denegación de servicio). Por eso estos servicios se quedan en la red interna.

19. Conclusiones

La práctica permitió desplegar una aplicación completa repartida en cinco contenedores con un solo archivo compose.yaml. La red interna y el DNS de Docker permiten que los servicios se encuentren por nombre sin depender de IP. El volumen nombrado separa los datos del ciclo de vida del contenedor, como se comprobó al recrear MariaDB sin perder información. Los health checks y depends_on garantizan un orden de arranque confiable.

Redis mostró una integración real: el listado se sirvió desde la caché, la caché se invalidó en cada cambio y el contador aumentó con cada consulta. Mailpit permitió verificar el envío de notificaciones sin enviar correo real. Por último, publicar solo los puertos necesarios y mantener las contraseñas fuera del repositorio reduce la superficie de ataque, una práctica básica para cualquier despliegue.
